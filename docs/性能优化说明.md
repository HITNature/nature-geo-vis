## 性能问题与目标

### 原始痛点

在地图上点击聚类点放大到详细级别后，曾出现：

- **FPS 骤降至个位数**（目标 60+）
- **缩放 / 拖动严重延迟**，需等待 rendering 完成
- **主线程被 DOM 与重绘占满**，Tooltip 与 UI 几乎无响应

### 优化成果（对外可引用）

| 场景 | 优化前 | 优化后 |
|------|--------|--------|
| 点击聚类点放大 | 卡顿 3–5 秒 | 流畅过渡（约 60ms 量级） |
| 高缩放级别拖动 | FPS &lt; 10 | FPS 60+ |
| 数据点悬停 | 无明显响应 | 即时 Canvas Tooltip |
| 视口 BBox 查询 | 全量内存线性扫描 | SQLite R-Tree 空间索引 |

**核心结论**：把瓶颈从「前端 DOM 爆炸 + 服务端全表扫描」迁移到「索引化查询 + 单 Canvas / Worker 绘制」，交互帧率回到可用水准。

## 全链路架构与开销分布

### 架构分层

```
┌─────────────────────────────────────────────────────────────┐
│                         用户浏览器                           │
│  ┌─────────────┐  ┌──────────────────┐  ┌────────────────┐ │
│  │ 地图瓦片 CDN │  │ Canvas / Offscreen│  │ React 交互层   │ │
│  │ (GPU/网络)  │  │ Worker 点位渲染   │  │ (主线程/DOM)   │ │
│  └─────────────┘  └──────────────────┘  └────────────────┘ │
│         ▲  PerfTracker（FPS / 耗时 / 计数 / 事件流）         │
└─────────────────────────────────────────────────────────────┘
                              │ HTTP / GeoJSON（按视口）
                              ▼
┌─────────────────────────────────────────────────────────────┐
│              Express + better-sqlite3（生产路径）              │
│  ┌──────────────┐  ┌────────────────┐  ┌─────────────────┐ │
│  │ R-Tree BBox  │  │ 行政层级预聚合 │  │ JSON 序列化输出 │ │
│  │ 空间索引查询 │  │ 省 / 市 / 区   │  │                 │ │
│  └──────────────┘  └────────────────┘  └─────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

### 开销分布与治理状态

| 环节 | 层级 | 主要开销 | 优化前 | 当前状态 |
|------|------|----------|--------|----------|
| 数据查询 | 服务端 | CPU / I/O | GeoJSON 全量进内存 + `.filter()` | **SQLite R-Tree 视口查询** ☑ |
| 聚类 / LOD | 服务端 | CPU | 运行时动态聚合压力大 | **四级行政预聚合 + 按 zoom 下发** ☑ |
| 网络传输 | 网络 | 带宽 / 延迟 | 大视口全量 GeoJSON | 按 bbox / zoom 裁剪（文本协议仍有优化空间） |
| 地图底图 | 前端 | GPU / 网络 | 默认瓦片行为 | **预加载缓冲 + 空闲更新 + 淡入** ☑ |
| **点位渲染** | **前端** | **主线程** | **数千 DOM Marker** | **Canvas 统一绘制；可选 OffscreenCanvas Worker** ☑ |

## 已落地的核心优化

### 1. SQLite R-Tree 空间索引查询（服务端）

**相关文件**：`scripts/import-to-sqlite.js`、`server/index-sqlite.js`

**问题**：早期路径将 POI / 网格载入内存，每次拖动对全量数组做 BBox 碰撞，查询成本随数据量线性增长。

**方案**：

- 导入阶段为 `cities` / `cells` / `pois` 建立 SQLite `rtree` 虚拟表
- API 通过 `INNER JOIN *_rtree` 按视口矩形检索，只返回可见要素
- 生产默认入口为 `npm run server` → `server/index-sqlite.js`

```sql
-- 示意：POI 视口查询走空间索引
SELECT p.* FROM pois p
INNER JOIN pois_rtree r ON p.id = r.id
WHERE r.max_x >= ? AND r.min_x <= ?
  AND r.max_y >= ? AND r.min_y <= ?;
```

**价值主张**：把「全国数据」变成「当前屏幕数据」，服务端可扩展到更大体量而不拖垮交互路径。

---

### 2. 多级 LOD：行政层级预聚合

**相关文件**：`server/config.js`、`scripts/import-to-sqlite.js`、`src/components/MapView.jsx`

**问题**：全国近 8 万 POI 若在低缩放级别全部绘制，网络与渲染双重过载。

**方案**：导入时预计算省 / 市 / 区聚合表，前端按缩放级别切换展示粒度：

| Zoom 区间（配置） | 展示层级 | 效果 |
|-------------------|----------|------|
| 0–7 | 省级聚合 | 宏观概览，节点极少 |
| 8–10 | 市级聚合 | 区域对比 |
| 11–12 | 区县级聚合 | 进入细节前的过渡 |
| ≥ 13 | 详细 POI（bbox） | Canvas 精确点位 |

这是面向地图场景的 **LOD（Level of Detail）**：不是简单「少画点」，而是用语义化行政聚合保证信息密度与性能的平衡。

### 3. Canvas 渲染替代 DOM Marker（前端主路径）

**文件**：`src/components/CanvasMarkerLayer.jsx`

**问题**：每个 POI 一个 React `<Marker>` + DOM 节点，放大后数千节点导致：

- DOM 创建 / 销毁与布局抖动
- React 虚拟 DOM Diff 成本飙升
- 主线程掉帧，拖动 FPS 跌至个位数

**方案**：Leaflet Canvas Renderer，所有点共享同一 Canvas：

```javascript
const circleMarker = L.circleMarker([lat, lng], {
    renderer: canvasRenderer  // 视口内点位共用一层 Canvas
});
```

| 指标 | 优化前 (DOM) | 优化后 (Canvas) |
|------|--------------|-----------------|
| DOM 节点数 | ~3000+ | 1（Canvas 层） |
| Marker 渲染 | 800–1500ms | &lt; 50ms（实测约 35ms） |
| 拖动 FPS | &lt; 10 | 60+ |

**这是交互体验跃迁的主因**，也是宣讲中最适合做前后对比演示的卖点。

---

### 4. OffscreenCanvas + Web Worker（可选增强路径）

**文件**：`src/components/OffscreenCanvasLayer.jsx`、`src/workers/render-worker.js`

在完成 Canvas 主路径后，进一步把**像素级绘制**迁出主线程：

1. `transferControlToOffscreen()` 将 Canvas 控制权交给 Worker
2. Worker 内完成点位绘制；主线程专注地图交互与 React
3. 通过 PERF MONITOR 一键切换 **Canvas / OffscreenCanvas**，便于 A/B 对比

```javascript
const worker = new Worker(
    new URL('../workers/render-worker.js', import.meta.url),
    { type: 'module' }
);
worker.postMessage({ type: 'INIT', canvas: offscreen }, [offscreen]);
```

**工程判断**：

| 做法 | 结论 |
|------|------|
| Worker 里做 `fetch` + `JSON.parse` | 收益有限（I/O 本就异步，且有 structured clone 成本）→ **已弃用该路线** |
| Worker 里做 OffscreenCanvas 绘制 | 适合高密度点场景，主线程占用显著下降 → **已实现并可演示** |
| Geometry Worker（BBox / 动态聚类） | 能力代码已就绪（`geometry-worker.js`），当前服务端预聚合已覆盖主路径，作为扩展储备 |

详细选型见 [`WEB_WORKER_GUIDE.md`](./WEB_WORKER_GUIDE.md)。

**文件**：`src/components/MapView.jsx`、`src/utils/perf.js`

## 实时性能观测体系

### 核心模块：`src/utils/perf.js`

自研轻量 `PerfTracker`，统一采集：

```javascript
class PerfTracker {
    metrics = {
        fps: 0,              // 实时帧率
        loadTimes: {},       // 各环节耗时
        counts: {},          // 瓦片 / Marker / Cluster 计数
        history: [],         // 事件日志
        benchmarks: {}       // A/B 采样均值
    };
}
```

### 关键指标与健康阈值

| 指标 | 类型 | 说明 | 健康阈值 |
|------|------|------|----------|
| `FPS` | 计数 | 主线程帧率 | &gt; 30（目标 60） |
| `Tiles Loading` | 计数 | 在途底图瓦片 | 不宜长期 &gt; 0 |
| `Cluster Nodes` | 计数 | 当前聚合节点 | 通常 &lt; 500 |
| `Markers (Detail)` | 计数 | 详细 POI 点数 | 随视口变化 |
| `Fetch Detailed POIs` | 耗时 | 详情数据往返 | 建议 &lt; 500ms |
| `Canvas` / Worker Render | 耗时 | 绘制耗时 | 建议 &lt; 100ms |

### UI：`src/components/PerformanceMonitor.jsx`

- URL 带 `?perf` 开启左上角浮动面板（演示时不干扰正式 UI）
- 实时 FPS、计数器、耗时与事件流
- **OFFSCREEN CANVAS** 开关：同屏对比主线程 Canvas vs Worker 渲染
- 支持折叠为 `PERF` 徽章，适合投屏讲解

## 地图瓦片与交互体验

### 已启用的 Leaflet 策略

```javascript
<TileLayer
    url="https://{s}.basemaps.cartocdn.com/dark_all/{z}/{x}/{y}{r}.png"
    className="dark-map-tiles"
    keepBuffer={4}             // 视口外缓冲，减少拖动白屏
    updateWhenZooming={false}  // 缩放动画期间不刷瓦片
    updateWhenIdle={true}      // 空闲后再更新，降低抖动
    maxNativeZoom={18}
    maxZoom={20}
    crossOrigin="anonymous"
/>
```

### CSS 层体验优化（`src/index.css`）

- `.leaflet-tile` 淡入过渡，降低「瓦片闪现」
- `translateZ(0)` / `will-change` 启用合成层，拖动更稳
- `.dark-map-tiles` 亮度滤镜：在暗色底图上保证红绿点 / 白字对比度（业务可读性优先）

### 底图策略说明

| 方案 | 状态 | 说明 |
|------|------|------|
| CARTO Dark CDN | **当前生产使用** | 美观、全球 CDN、零运维 |
| OSM / Mapbox / 自托管 | 备选 | 可按合规或内网要求切换 |
| Service Worker 瓦片缓存 | 路线图 | 进一步降低重复拉取与弱网抖动 |

- **设备**：MacBook Pro M1
- **浏览器**：Chrome 120
- **数据规模**（`data/geodata.db`，约 425MB）：

| 图层 | 数量 | 备注 |

| 指标 | 时间 |
|------|------|

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| Marker 渲染（DOM） | ~1200ms | — |
| Marker 渲染（Canvas） | — | ~35ms |
| 端到端感知延迟 | ~1400ms | ~60ms 量级 |

### 场景 3：高缩放级别拖动

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| FPS | 5–15 | 60+ |

## 技术演进路线图

### 已完成优化

| 能力 | 状态 | 落点 |
|------|------|------|
| R-Tree 空间索引 + 视口 API | ☑ | `geodata.db` / `index-sqlite.js` |
| 四级行政 LOD 预聚合 | ☑ | 导入脚本 + zoom 配置 |
| Canvas 点位渲染 | ☑ | `CanvasMarkerLayer.jsx` |
| OffscreenCanvas Worker 渲染 | ☑（可切换） | `OffscreenCanvasLayer` + `render-worker.js` |
| 实时 Perf Monitor + A/B 开关 | ☑ | `?perf` |
| 瓦片预加载 / 空闲更新 / 淡入 | ☑ | `MapView` + CSS |

### 下一阶段进阶（网络与传输）

1. **矢量瓦片 (MVT)**：以二进制矢量瓦片替代大块 GeoJSON，进一步压低带宽与解析成本（仓库内留有 `geojson-vt` 探索路径，尚未接入主链路）
2. **Protobuf / 紧凑二进制协议**：属性字段多时显著小于 JSON
3. **渐进式视口加载**：中心区域优先、边缘补齐，缩短首屏可交互时间
4. **PWA 瓦片缓存**：Service Worker `CacheFirst` 缓存底图，改善弱网与二次访问
5. **Geometry Worker 接入主路径**：在需要客户端动态聚类 / 复杂几何运算时启用已有 `geometry-worker.js`
